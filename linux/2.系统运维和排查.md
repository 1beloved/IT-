## 第 2 周：系统运维与故障排查

**目标：能系统性回答「这个服务为什么访问不了」。**

### 2.1 systemd 与服务管理

systemd 是现代 Linux 的初始化系统（PID 1），管理服务、挂载、定时器等，被管理的对象叫 **unit**。

```bash
systemctl status nginx          # 状态 + 最近几行日志（排障第一步）
systemctl start|stop|restart|reload nginx
systemctl enable --now nginx    # 开机自启并立即启动
systemctl disable nginx
systemctl is-active nginx; systemctl is-enabled nginx
systemctl list-units --type=service --state=running
systemctl --failed              # 列出失败的服务
systemctl daemon-reload         # 修改 unit 文件后必须执行
```

- `restart` 会中断连接；`reload` 重新加载配置而不断连（服务需支持）。
- `enable` 管「开机是否自启」，`start` 管「现在是否运行」，两者独立。
- unit 文件位置：`/lib/systemd/system/`（包自带）、`/etc/systemd/system/`（自己写 / 覆盖，优先级更高）。

### 2.2 日志

|   |   |
|---|---|
|位置|内容|
|`/var/log/syslog`（Ubuntu）/ `messages`（RHEL）|系统综合日志|
|`/var/log/auth.log`（Ubuntu）/ `secure`（RHEL）|登录与认证，查爆破|
|`/var/log/kern.log`、`dmesg`|内核、硬件、OOM|
|`/var/log/nginx/`|Nginx 访问与错误日志|

```bash
journalctl -u nginx -n 100 --no-pager     # 某服务最近 100 行
journalctl -u nginx -f                    # 实时跟踪
journalctl --since '1 hour ago' -p err    # 近 1 小时的 error 及以上
journalctl -b                             # 本次启动以来
journalctl --disk-usage
last; lastb; who                          # 登录记录 / 失败登录 / 当前在线
dmesg -T | grep -i -E 'oom|error'         # 内核日志，查内存被杀
```

日志轮转由 `logrotate` 负责，配置在 `/etc/logrotate.d/`，作用是按天/大小切割、压缩、保留 N 份，防止日志撑满磁盘。

### 2.3 SSH

```bash
ssh ops@192.168.1.10 -p 22
ssh-keygen -t ed25519 -C 'my-laptop'      # 生成密钥对
ssh-copy-id ops@192.168.1.10              # 把公钥放到服务器
scp file ops@host:/tmp/                   # 拷贝文件
rsync -avz --delete src/ ops@host:/dst/   # 增量同步（比 scp 更适合备份）
ssh -L 8080:127.0.0.1:80 ops@host         # 本地端口转发
```

密钥登录原理：客户端持私钥，服务器 `~/.ssh/authorized_keys` 存公钥；**权限必须严格**，否则 sshd 拒绝：

```bash
chmod 700 ~/.ssh && chmod 600 ~/.ssh/authorized_keys
```

客户端 `~/.ssh/config` 简化连接：

```
Host web1
    HostName 192.168.1.10
    User ops
    IdentityFile ~/.ssh/id_ed25519
```

服务端加固（`/etc/ssh/sshd_config`）：

```
PermitRootLogin no
PasswordAuthentication no     # 确认密钥登录成功后再关！
#Port 22 可改端口，但不是安全的根本
```

改完先 `sudo sshd -t` 检查语法，再 `sudo systemctl reload ssh`（RHEL 系服务名是 `sshd`）。**保持一个已登录的会话不要断**，新开窗口测试成功再关旧的。

常见报错：

|   |   |
|---|---|
|现象|常见原因|
|`Connection refused`|sshd 没启动 / 端口不对 / 被防火墙明确拒绝|
|`Connection timed out`|网络不通 / 防火墙或云安全组丢包 / IP 错|
|`Permission denied (publickey)`|公钥没放对 / 权限不对 / 用户名错|
|`REMOTE HOST IDENTIFICATION HAS CHANGED`|服务器重装过，`ssh-keygen -R host` 清旧记录|

### 2.4 网络基础命令

|   |   |   |
|---|---|---|
|目的|命令|网络设备类比|
|看接口与 IP|`ip a`（`ip -br a` 简洁）|`show ip interface brief`|
|看路由表|`ip r`|`show ip route`|
|看 ARP 邻居|`ip neigh`|`show arp`|
|看监听与连接|`ss -tulnp`|`show tcp brief`|
|连通性 / 路径|`ping`、`traceroute`、`mtr`|`ping`、`traceroute`|
|抓包|`tcpdump -i any -nn port 80`|`debug` / SPAN 抓包|
|DNS 查询|`dig example.com`、`nslookup`|—|
|HTTP 测试|`curl -v http://host/`|—|

要点：

- **IP**：`ip a` 看到 `inet 192.168.1.10/24` 即地址与掩码；Ubuntu 用 netplan 持久化配置（`/etc/netplan/*.yaml`，改完 `sudo netplan apply`），RHEL 系用 NetworkManager（`nmcli`）。
- **路由**：重点看 `default via x.x.x.x dev ens33`，没有默认路由就出不了本网段。
- **DNS**：`/etc/hosts`（本地静态解析，优先）、`/etc/resolv.conf`（DNS 服务器）；Ubuntu 上 `resolvectl status` 看真实 DNS。`dig +short example.com` 能解析而 `curl` 不行，多半是应用层问题。
- 主机名：`hostnamectl set-hostname web1`。

### 2.5 端口与监听

```bash
ss -tulnp          # t TCP u UDP l 监听 n 数字 p 进程
ss -tnp state established   # 已建立连接
lsof -i :80        # 谁占用了 80
nc -zv 10.0.0.5 80 # 测试远端端口是否通（不依赖 ping）
```

看懂监听地址最关键：

- `0.0.0.0:80` / `*:80`：所有 IPv4 地址可访问
- `127.0.0.1:80`：**只有本机能访问**（外部访问失败的常见原因！）
- `[::]:80`：IPv6（通常同时覆盖 IPv4）

### 2.6 防火墙

概念：Linux 内核用 netfilter 过滤包，`iptables` / `nftables` 是底层工具，日常用上层封装。

```bash
# Ubuntu：ufw
sudo ufw status verbose
sudo ufw allow 22/tcp && sudo ufw allow 80/tcp
sudo ufw enable                # 先放行 22 再启用，否则把自己锁在外面

# RHEL 系：firewalld
sudo firewall-cmd --state
sudo firewall-cmd --list-all
sudo firewall-cmd --permanent --add-service=http
sudo firewall-cmd --permanent --add-port=8080/tcp
sudo firewall-cmd --reload     # permanent 规则要 reload 才生效

sudo iptables -L -n -v         # 查看底层规则
```

补充两点：

- **云服务器还有「安全组」**，它在系统外面，系统内放行了但安全组没放，照样访问不了。
- **SELinux**（RHEL 系）：`getenforce` 查看状态。排障时可 `setenforce 0` 临时切到宽容模式验证是否是它导致；若是，应该用 `restorecon` 或调整布尔值 / 上下文修复，而不是永久关闭。

### 2.7 排障方法论：「服务为什么访问不了」

**自下而上、逐层缩小范围**，每一步只回答一个问题：

|   |   |   |
|---|---|---|
|步骤|要回答的问题|命令|
|1|服务进程在运行吗？|`systemctl status svc`|
|2|有没有监听正确的地址和端口？|`ss -tulnp \| grep :80`|
|3|本机自己能访问吗？|`curl -I http://127.0.0.1`|
|4|配置和日志有报错吗？|`journalctl -u svc -n 50`、`tail error.log`|
|5|本机防火墙放行了吗？|`ufw status` / `firewall-cmd --list-all`|
|6|网络层可达吗？|`ping`、`ip r`、`traceroute`|
|7|域名解析对吗？|`dig`、`/etc/hosts`|
|8|外部还有阻挡吗？|云安全组、上游 ACL、客户端自身|

**从报错现象反推：**

|   |   |
|---|---|
|现象|倾向原因|
|`Connection refused`|主机可达，但端口没监听，或被 REJECT|
|超时 timeout|被 DROP / 路由不通 / 安全组 / IP 写错|
|`Name or service not known`|DNS 问题|
|HTTP 403|权限 / 目录 index / 访问控制|
|HTTP 404|路径或 root 配错|
|HTTP 502 / 504|反向代理的后端没起或太慢|
|本机 curl 通、外部不通|监听在 127.0.0.1，或防火墙 / 安全组|

### 2.8 第 2 周自测清单

- 故意 `systemctl stop nginx`、改错端口、关防火墙，分别用上表定位
- 配好密钥登录并禁用密码登录与 root 登录
- 说清 `Connection refused` 与 `timed out` 的区别
- 用 `ss`、`journalctl`、`tcpdump` 各抓出一个问题证据
