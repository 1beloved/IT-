# IP SLA 详解

## 1. 什么是 IP SLA

**IP SLA(Internet Protocol Service Level Agreement)** 是 Cisco IOS 内置的主动式网络性能探测功能。设备作为"探测源"(Source)向目标发送合成流量,测量延迟、抖动、丢包、可达性等指标,并可把结果与其他功能(如路由、HSRP、EEM)联动。

它与 SNMP 这类被动监控不同:IP SLA 是**主动产生探测流量**,所以能在真实业务出问题之前发现问题。

## 2. 主要用途

|场景|说明|
|---|---|
|**链路/路径可达性检测**|判断下一跳、ISP 出口、远端服务器是否真的可达|
|**性能监控**|测量 RTT、单向延迟、抖动、丢包、MOS(VoIP 质量)|
|**浮动静态路由 / 双出口冗余**|主链路探测失败时自动撤销主路由,切到备份|
|**HSRP/VRRP 优先级联动**|上联链路故障时降低优先级触发主备切换|
|**PBR 联动**|策略路由的下一跳失效时自动回退|
|**SLA 合规验证**|验证运营商是否满足延迟、丢包承诺|
|**应用服务检测**|探测 HTTP、DNS、DHCP、FTP 等服务是否正常|

## 3. 工作原理

IP SLA 由以下几部分组成:

- **Source(源端)**:配置并运行探测操作的设备
- **Responder(响应端)**:可选,目标设备上启用后可提供更精确的时间戳,支持单向延迟测量及 UDP Jitter 等操作
- **Operation(操作)**:探测类型和参数,用编号标识
- **Schedule(调度)**:操作必须被调度才会运行
- **Statistics/History(统计与历史)**:保存结果,可通过 CLI 或 SNMP 获取

探测流程是:Source 按设定频率发送探测包,Responder 或目标主机应答,Source 计算指标并更新统计。

## 4. 常见探测类型

- **ICMP Echo**:最常用,检测连通性和 RTT,无需 Responder
- **ICMP Path-Echo / Path-Jitter**:逐跳探测路径
- **UDP Echo**:测 UDP 端口往返时延
- **UDP Jitter**:测单向延迟、抖动、丢包,需要 Responder,常用于 VoIP 质量评估
- **TCP Connect**:检测 TCP 端口是否可建立连接
- **HTTP**:检测 Web 服务,可测 DNS、TCP 连接、事务时间
- **DNS**:测 DNS 解析时间
- **DHCP**:测 DHCP 服务器响应
- **FTP**:测 FTP 下载时间
- **VoIP 相关**:UDP Jitter for VoIP 等

## 5. 基本配置

### 5.1 创建一个 ICMP Echo 探测

```
ip sla 10
 icmp-echo 8.8.8.8 source-interface GigabitEthernet0/0
 frequency 10
 timeout 2000
 threshold 1000
exit
ip sla schedule 10 life forever start-time now
```

关键参数:

- `frequency`:探测间隔(秒)
- `timeout`:等待响应的超时(毫秒)
- `threshold`:延迟阈值(毫秒),超过会触发 Over Threshold 事件
- `life forever`:永久运行
- `start-time now`:立即开始

### 5.2 查看结果

```
show ip sla configuration 10
show ip sla statistics 10
show ip sla summary
```

### 5.3 UDP Jitter 与 Responder

源端:

```
ip sla 20
 udp-jitter 10.1.1.2 16384 num-packets 20 interval 20
 frequency 60
ip sla schedule 20 life forever start-time now
```

目标端:

```
ip sla responder
```

## 6. 与 Track 联动(最经典的应用)

IP SLA 本身只产生探测结果,**真正发挥作用要靠 Track 对象**把探测结果转成"Up/Down"状态,再由路由、HSRP 等引用。

### 6.1 浮动静态路由双出口

```
ip sla 1
 icmp-echo 203.0.113.1 source-interface GigabitEthernet0/0
 frequency 5
ip sla schedule 1 life forever start-time now

track 1 ip sla 1 reachability

ip route 0.0.0.0 0.0.0.0 203.0.113.1 track 1
ip route 0.0.0.0 0.0.0.0 198.51.100.1 250
```

逻辑:

- 主出口探测成功,Track 为 Up,主默认路由(AD=1)生效
- 探测失败,Track 变 Down,主路由被撤销,AD=250 的备份路由接管
- 探测恢复后,主路由自动回归

> 这解决了普通静态路由的痛点:接口 up 但上游链路已断时,静态路由不会消失,流量会被黑洞掉。

### 6.2 Track 的两种状态判定

```
track 1 ip sla 1 reachability   ! 根据成功/失败判断
track 2 ip sla 1 state          ! 根据 OK/非 OK 状态判断
```

还可以设置延迟:

```
track 1 ip sla 1 reachability
 delay down 10 up 20
```

用来防止链路抖动造成路由频繁震荡。

### 6.3 联动 HSRP

```
track 1 ip sla 1 reachability
interface GigabitEthernet0/1
 standby 1 ip 192.168.1.1
 standby 1 priority 110
 standby 1 preempt
 standby 1 track 1 decrement 20
```

### 6.4 联动 EEM

可以在 Track 状态变化时用 EEM 脚本执行动作,如发送 Syslog、切换配置、发邮件等。

## 7. 阈值与告警

可以配置 Reaction(反应)来对异常做出响应:

```
ip sla reaction-configuration 10 react timeout threshold-type immediate action-type trapOnly
ip sla reaction-configuration 10 react rtt threshold-value 200 100 threshold-type immediate action-type trapOnly
```

支持的动作包括发送 SNMP Trap、触发另一个 IP SLA 操作等。

## 8. 优点与局限

**优点**

- 设备自带,无需额外硬件或软件
- 探测类型丰富
- 能与路由、HSRP、EEM 等联动实现自动化故障切换
- 可通过 SNMP 集成到网管平台

**局限**

- 探测本身占用设备 CPU 和带宽,大规模、高频探测要谨慎
- ICMP 探测结果可能受目标限速或被防火墙过滤影响
- 单个目标探测失败不一定代表链路真断,生产中建议探测**多个目标**,配合 Track 的布尔组合(`track X list boolean or/and`)提高可靠性
- UDP Jitter 等高级功能需要 Responder 支持

## 9. 排错要点

|现象|排查方向|
|---|---|
|操作一直 Pending|是否忘记 `ip sla schedule`|
|探测总是失败|源接口/源 IP 是否正确,目标是否回包,路由与 ACL|
|Track 状态不变化|检查 `show track`,确认类型是 reachability 还是 state|
|路由没有被撤销|确认静态路由语句末尾确实加了 `track N`|
|UDP Jitter 无结果|目标端是否启用 `ip sla responder`|

常用命令:

```
show ip sla statistics
show ip sla configuration
show track
show ip route
debug ip sla trace
```

## 10. 小结

IP SLA 的核心价值是:**用主动探测把"链路是否真正可用"这个问题量化,并通过 Track 驱动路由和高可用机制自动调整**。最典型、也是考试和实战中最常见的组合就是 **IP SLA + Track + 静态路由/HSRP**。
