# BFD 详解

## 1. 什么是 BFD

**BFD(Bidirectional Forwarding Detection,双向转发检测,RFC 5880)** 是一个轻量级的、与具体协议无关的**快速故障检测机制**。它只做一件事:**在两个设备之间以极短的间隔互发小报文,尽快发现它们之间的转发路径是否中断**,然后通知上层协议(OSPF、EIGRP、BGP、静态路由、HSRP 等)去收敛。

BFD 本身不计算路由,只负责"快速发现故障并通知"。

## 2. 为什么需要 BFD

先看传统协议检测故障有多慢:

| 机制         | 默认检测时间                                 |
| ---------- | -------------------------------------- |
| OSPF       | Hello 10s / Dead 40s(可调到亚秒级,但 CPU 开销大) |
| EIGRP      | Hello 5s / Hold 15s                    |
| BGP        | Keepalive 60s / Hold 180s              |
| 接口 down 检测 | 物理层断开才能立即发现                            |

**两个痛点:**

1. **慢**:协议 Hello 要靠控制平面处理,间隔压得太低会吃 CPU,秒级基本是极限
2. **物理层 up 但转发已断**:两台路由器中间隔着交换机、光电转换器、运营商二层网络(如 MetroE、VPLS)时,一端的接口依然 up/up,但对端其实已经不可达,只能等协议超时

BFD 把检测做得**足够轻、足够快**(毫秒级),并且让各协议共用同一个检测机制,不必各自把 Hello 调到极限。

## 3. 工作原理

### 3.1 基本过程

```
 R1                                   R2
 │ ── BFD Control 包(UDP 3784)──────▶ │
 │ ◀────── BFD Control 包 ─────────── │
 │   按协商好的间隔持续互发             │
 │                                    │
 连续 N 个检测周期没收到对端的包 → 判定 Down → 通知上层协议
```

- 报文封装在 **UDP** 中:单跳 BFD 用目的端口 **3784**,多跳 BFD 用 **4784**,Echo 模式用 **3785**
- 报文很小,在转发平面/硬件上处理,CPU 开销低,因此可以做到 50ms~300ms 级别的间隔

### 3.2 会话状态机与握手

BFD 会话有四种状态:

| 状态            | 含义                  |
| ------------- | ------------------- |
| **AdminDown** | 管理上关闭               |
| **Down**      | 会话不存在或对端不可达         |
| **Init**      | 已收到对端报文,但对端还没确认收到我的 |
| **Up**        | 双向都确认,会话建立          |

建立过程是**三次握手**,双方通过报文里的 **Discriminator(标识符)** 区分会话,并在报文中携带自己的状态,直到双方都进入 Up。

### 3.3 协商的三个参数

```
interface Ethernet0/0
	bfd interval 300 min_rx 300 multiplier 3
```

| 参数           | 含义                               | 例子                |
| ------------ | -------------------------------- | ----------------- |
| `interval`   | 我**希望发送**报文的间隔(Desired Min TX)   | 本端⼤约每 300ms 发⼀次   |
| `min_rx`     | 我**最小能接收**报文的间隔(Required Min RX) | 希望对端不要低于 300ms 发来 |
| `multiplier` | 倍数,连续丢多少个包才判 Down                | 连续 3 次没收到就 Down   |

两端协商后的结果:

- **实际发送间隔** = max(本端 interval,对端 min_rx)
- **检测时间(Detection Time)** = 对端的 multiplier × 对端发送间隔

例如两端都是 `300 / 300 / 3`:检测时间 = 3 × 300ms = **900ms**。比 OSPF 默认的 40 秒快了很多。

## 4. 两种工作模式

### 4.1 异步模式(Asynchronous,默认)

双方**周期性地互相发送**控制报文,一方在检测时间内没收到对端的包,就判 Down。这是最常用、必须有的模式,会话也靠它建立。

### 4.2 Echo 模式

一方发出的 Echo 报文,**由对端的转发平面直接环回**,对端的 BFD 进程不参与处理:

```
 R1 ── Echo 包(源和目的都是 R1 的地址)──▶ R2 ──(按普通转发环回)──▶ R1
```

特点:

- 检测的是**对端转发平面**是否正常,更接近真实业务路径
- 对端 CPU 几乎无负担
- 启用 Echo 后,异步模式的控制报文间隔会放慢(Cisco 上降到约 1 秒),因为主要靠 Echo 做快速检测
- 部分平台默认开启,可通过 `no bfd echo` 关闭;使用 Echo 时接口通常建议 `no ip redirects`,避免对端对环回报文发 ICMP Redirect

另外还有 **Demand 模式**(会话建立后停止周期报文,需要时再探测),在 Cisco 常见实现中很少用到,了解即可。

## 5. 配置

BFD 的配置分两层:**接口上定义参数**,**协议里启用 BFD**。

### 5.1 接口参数

```
interface GigabitEthernet0/0
 ip address 10.1.1.1 255.255.255.0
 bfd interval 300 min_rx 300 multiplier 3
```

### 5.2 与各协议联动

**OSPF**

```
router ospf 1
 bfd all-interfaces
! 或在单个接口上
interface Gi0/0
 ip ospf bfd
```

**EIGRP**

```
router eigrp 100
 bfd all-interfaces/bfd interface g0/0
```

**BGP**(邻居级别)

```
router bgp 65001
 neighbor 10.1.1.2 remote-as 65002
 neighbor 10.1.1.2 fall-over bfd
```

**静态路由**

```
ip route static bfd GigabitEthernet0/0 10.1.1.2
ip route 192.168.0.0 255.255.0.0 GigabitEthernet0/0 10.1.1.2
```

BFD 会话 Down 时,绑定它的静态路由被撤销。

**HSRP**

```
interface Gi0/1
 standby bfd
```

### 5.3 多跳 BFD

用于两台非直连设备之间(如 BGP 的 loopback 邻居),需要先定义 bfd-map 和 bfd 模板,配置较复杂,且不同平台差异大,使用时查对应版本文档。

## 6. 验证与排错

```
show bfd neighbors
show bfd neighbors details
show bfd summary
```

典型输出:

```
NeighAddr       LD/RD       RH/RS     State    Int
10.1.1.2        1/1         Up        Up       Gi0/0
```

|字段|含义|
|---|---|
|`LD/RD`|本端/对端 Discriminator,两端要对得上|
|`State`|**Up** 为正常|
|`Int`|会话所在接口|

`details` 中能看到协商后的间隔、检测时间、**注册了哪些协议**(`Registered protocols: OSPF` 等)。如果协议列表是空的,说明协议侧没有真正启用 BFD。

常见问题:

|现象|可能原因|
|---|---|
|会话一直 Down/Init|对端没启用 BFD,或 UDP 3784 被 ACL 拦截|
|会话 Up 但协议没联动|协议里没配 `bfd all-interfaces` 或 `fall-over bfd`|
|会话频繁 flap|间隔太激进、链路质量差、CPU 高,应放宽间隔或加大 multiplier|
|两端参数不同|不影响建立,以协商结果为准,但检测时间可能和预期不同|

## 7. 与 IP SLA 对比

这和你前面学的内容直接相关,两者解决的都是"检测故障",但定位不同:

|      | **BFD**               | **IP SLA**               |
| ---- | --------------------- | ------------------------ |
| 检测对象 | 两个**相邻/指定对端**之间的转发路径  | 任意**远端目标**(端到端)          |
| 对端要求 | **对端必须也运行 BFD**       | 不需要,对方能响应 ICMP 等即可       |
| 检测速度 | **毫秒级到亚秒级**           | 秒级(frequency 通常 ≥ 1 秒)   |
| 机制   | 双方互发,握手建立会话           | 单方主动探测                   |
| 通知方式 | 直接通知注册的协议(OSPF/BGP 等) | 借助 **Track** 转成 Up/Down  |
| 能测什么 | 只有"通/不通"              | RTT、抖动、丢包、HTTP/DNS 等性能指标 |
| 典型场景 | 设备间/运营商二层链路的快速收敛      | ISP 出口检测、浮动静态路由、SLA 验证   |

**用你前面的场景串起来:**

- 企业连 ISP,ISP **不会配合跑 BFD** → 只能用 IP SLA 单方探测
- 企业内部核心/汇聚之间跑 OSPF,中间隔着二层设备 → 用 BFD 让 OSPF 秒级收敛
- 和 ISP 跑 eBGP 且 ISP **支持 BFD** → BGP + BFD 是最理想组合

两者**不是替代关系**:BFD 偏"快速发现邻居链路故障",IP SLA 偏"端到端可达性与性能监控"。

## 8. 使用注意事项

1. **不要把间隔压得过低**:50ms 级别对硬件转发平台才合适,软件转发的路由器/虚拟设备上 300ms 以上更稳妥,否则容易误判
2. **BFD 检测的是链路,不是整个业务**:它只能说明"到这个邻居的路径通",邻居之后的网络是否正常它不管
3. **控制平面故障可能不被发现**:BFD 在转发平面处理,所以某些情况下**转发正常但协议进程有问题**,BFD 仍是 Up,协议要靠自己的 Hello 发现
4. **平台支持差异大**:是否支持硬件卸载、Echo、多跳、各协议联动,取决于具体型号和版本;GNS3/EVE-NG 里的虚拟镜像也不一定完整支持
5. **BFD 太敏感会引发震荡**:短暂抖动就触发协议重收敛,可能比慢检测更糟,生产中要权衡

## 9. 小结

- BFD 是一个**独立、通用、轻量的快速检测层**,把"发现故障"从各个协议里剥离出来统一做
- 核心机制:**双方互发 UDP 小包 + 三次握手 + 检测时间 = multiplier × 间隔**
- 价值:把故障检测从秒级、几十秒级降到**亚秒级**,并且对物理层 up 但转发中断的情况同样有效
- 与 IP SLA 的区别:BFD **需要对端配合**、速度快、只判通断;IP SLA 不需要对端配合、能测性能、速度较慢
